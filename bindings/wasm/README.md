# WhiteoutLib — WebAssembly bindings

This directory holds the Embind translation units that compile WhiteoutLib
to WebAssembly, plus a small amount of hand-written glue. It produces two
distinct WASM targets that ship as two distinct npm packages.

| Target              | npm package    | Environments      | Threading | Filesystem        | What it adds                                                  |
| ------------------- | -------------- | ----------------- | --------- | ----------------- | ------------------------------------------------------------- |
| `whiteout_wasm`     | `whiteout-wasm`| Browser **+** Node| single    | in-memory only    | Baseline: model + texture parse/write, math, MPQ in-memory.   |
| `whiteout_wasm_node`| `whiteout-node`| Node only         | pthreads  | direct disk (raw) | `OsFileSystem`, `SimpleThreadPool`, subclassable HttpHandler. |

`whiteout-node` is a *superset* of `whiteout-wasm` — any code that targets
the smaller package runs unchanged on the bigger one (modulo the import
specifier). Pick the smaller one unless you specifically need disk I/O or
multithreading.

## Layout

```
bindings/wasm/
├── CMakeLists.txt          Two add_executable targets driven by emcc.
├── bindings.cpp            Hand-written umbrella (InMemoryFileSystem,
│                           texture-format facades, Node-vs-web stubs).
├── node_bindings.cpp       Hand-written Node extras (pthread pool, etc.)
├── in_memory_fs.{h,cpp}    Spillover from the web build's missing FS.
├── optional_marshal.h      `std::optional<T>` ⇄ JS `null | T` adapter.
├── *_bindings.cpp          AUTOGENERATED by `tools/codegen/emit_embind.py`.
└── README.md               (this file)
```

The auto-generated `*_bindings.cpp` files carry an `AUTOGENERATED` banner.
Don't hand-edit them — change the C++ headers (or `tools/codegen/modules/`)
and re-run codegen.

## Building

Both targets require [emsdk](https://emscripten.org/docs/getting_started/downloads.html)
and Python ≥ 3.10 with the `libclang` bindings (the project's `.venv` already
has them; `pip install clang` if you're rolling your own).

### Browser + Node build (whiteout_wasm)

```pwsh
# from repo root
.\scripts\build-wasm.ps1
```

What that script does:

1. Runs the codegen for every wasm module (`mdx`, `m2`, `m3`, `textures`,
   `mpq`, `utils`) for the `embind` and `dts` backends.
2. Configures cmake with the Emscripten toolchain (`Ninja`, `Release`).
3. Builds `build-wasm/wasm-dist/whiteout.{js,wasm}`.
4. Stages the published layout into `packages/js-ts/` (the npm package).

### Node-only build (whiteout_wasm_node)

```pwsh
.\scripts\build-wasm-node.ps1
```

Same flow as above, but produces `whiteout-node.{js,wasm,worker.js}` into
`packages/js-node/` and uses pthreads + NODERAWFS.

### Re-codegen only (no rebuild)

If you only changed `@bind` annotations and want to refresh the bindings
without paying for an emcc compile:

```pwsh
$env:Path = "C:\Projects\WhiteoutLib\.venv\Scripts;$env:Path"
foreach ($mod in 'mdx','m2','m3','textures','mpq','utils') {
    python -m tools.codegen.codegen $mod
    python -m tools.codegen.codegen $mod --backend dts
}
```

## Browser usage (whiteout-wasm)

### Install

```sh
npm install whiteout-wasm
```

Pair it with a bundler that understands `.wasm` assets — Vite, esbuild,
webpack, or Parcel all work out of the box. There is no transpilation
step; the package ships ES2022 modules and TypeScript declarations.

### Minimal example: MDX → MDL

```ts
import Whiteout from 'whiteout-wasm';

const whiteout = await Whiteout();              // resolves once; cache it

async function mdxToMdl(file: File): Promise<Uint8Array> {
    const bytes = new Uint8Array(await file.arrayBuffer());

    const parser = new whiteout.mdx.Parser();
    try {
        const model = parser.parse_buffer_format(
            bytes, whiteout.mdx.MDLXFormat.MDX,
        );
        try {
            const writer = new whiteout.mdx.Writer();
            try {
                return writer.write_mdx_format_mdlFormat(
                    model,
                    whiteout.mdx.MDLXFormat.MDL,
                    whiteout.mdx.MdlFormat.WarcraftIII,
                );
            } finally { writer.delete(); }
        } finally { model.delete(); }
    } finally { parser.delete(); }
}
```

The library is **exception-free** — parsing a corrupt file yields a
best-effort `Model` plus a list of warnings on `parser.getIssues()`
(rather than throwing). The `delete()` pattern is mandatory because every
Embind handle owns a native WASM allocation.

The same flow via the higher-level facade (less typing, no manual
`.delete()`):

```ts
const model = whiteout.mdx.parse(bytes);                    // MDX bytes → Model
const mdlBytes = whiteout.mdx.writeMdl(
    model, whiteout.mdx.MdlFormat.Hiveworkshop,             // optional dialect
);
model.delete();
```

### Texture conversion

```ts
import Whiteout from 'whiteout-wasm';
const w = await Whiteout();

// BLP → PNG
const tex = w.blp.parse(await blpResponse.bytes());
try {
    const png = w.png.write(tex);
    download(png, 'out.png');
} finally { tex.delete(); }
```

Every texture format exposes the same shape: `w.<fmt>.parse(bytes)`,
`w.<fmt>.write(texture)`, plus the underlying `w.<fmt>.Parser` /
`w.<fmt>.Writer` Embind classes if you need finer control.

### Browser memory model

| Concept                | Implication                                                                 |
| ---------------------- | --------------------------------------------------------------------------- |
| Every native object    | Owns a heap allocation. Call `.delete()` (try/finally) when done.           |
| `Uint8Array` returns   | Already copied out of WASM heap — safe to keep after the native is gone.    |
| `Vector<u8>` returns   | A proxy to the WASM heap. The facade's `vecToBytes()` copies + frees it.   |
| `allocate_memory_growth` | Initial heap 64 MB, can grow up to 2 GB. Big models work; massive corpora may not. |

### Vite tip

The `whiteout-wasm` package contains both a `.js` loader and the sibling
`.wasm`. Vite's dep optimizer can mangle that pairing — exclude it:

```ts
// vite.config.ts
export default defineConfig({
    optimizeDeps: { exclude: ['whiteout-wasm'] },
    server: {
        // If your example sits outside the package directory, allow Vite's
        // /@fs/ route to reach into node_modules' real location.
        fs: { allow: ['..', '../..'] },
    },
});
```

A complete browser example lives at
[`examples/js-ts/mdl-mdx-converter/`](../../examples/js-ts/mdl-mdx-converter/)
— a Vite + TypeScript MDX↔MDL converter, drop-zone UI and all.

## Node.js usage (whiteout-node)

### Install

```sh
npm install whiteout-node
```

Requires Node ≥ 18. The package self-loads its `.wasm` (no bundler
needed) and starts up a pthread pool on first call.

### Same model API, plus disk and threads

```ts
import Whiteout from 'whiteout-node';
import { readFile, writeFile } from 'node:fs/promises';

const w = await Whiteout();

// 1. Read straight from disk (no copy through the FS-less browser path).
const mdxBytes = await readFile('Footman.mdx');

// 2. Convert MDX → MDL (text), HiveWorkshop dialect.
const model = w.mdx.parse(mdxBytes);
try {
    const mdlText = w.mdx.writeMdl(model, w.mdx.MdlFormat.Hiveworkshop);
    await writeFile('Footman.mdl', mdlText);
} finally { model.delete(); }
```

### Disk-backed VirtualPathFileSystem (M2 sibling-file resolution)

M2 models reference `.skin`, `.skel`, `.anim`, `.bone` siblings by path —
the Node build can resolve them directly off disk via `OsFileSystem`:

```ts
import Whiteout from 'whiteout-node';
const w = await Whiteout();

// The npm facade exposes OsFileSystem as a thin wrapper.
const m2 = w.m2.parseFromDisk('./Character/Human/Male/HumanMale.m2');
try {
    console.log(`bones:    ${m2.bones.size()}`);
    console.log(`textures: ${m2.textures.size()}`);
} finally { m2.delete(); }
```

### Multi-threaded mipmap generation

```ts
import Whiteout from 'whiteout-node';
const w = await Whiteout();

const pool = w.threadPool(8);                  // 8 worker threads
try {
    const tex = w.png.parse(pngBytes);
    try {
        tex.generateMipmaps_pool(pool);        // parallelises Kaiser filter
        const dds = w.dds.write(tex);
        await writeFile('out.dds', dds);
    } finally { tex.delete(); }
} finally { pool.delete(); }
```

`pool` is the same `interfaces::WorkerPool*` the C++ library expects —
the codegen exposes it as a first-class JS handle.

### Node-only extras at a glance

| API                                       | Purpose                                                     |
| ----------------------------------------- | ----------------------------------------------------------- |
| `w.OsFileSystem`                          | Read/write the host disk; implements `VirtualPathFileSystem`. |
| `w.threadPool(n)` / `w.SimpleThreadPool`  | Pre-spawned pthread pool for pool-aware C++ APIs.           |
| `w.makeHttpHandler(impl)`                 | Plug a JS HTTP backend into the C++ `HttpHandler` interface (online CASC). |
| MPQ on-disk                               | `Storage.open(path, pool)` reads .mpq from real files.      |

## TypeScript type surface

Both packages ship hand-written `index.d.ts` facades plus auto-generated
per-module type declarations under `types/`:

```
packages/js-ts/
├── index.d.ts            Facade (`whiteout.mdx`, `whiteout.png`, …)
├── types/
│   ├── mdx.d.ts          ← codegen --backend dts mdx
│   ├── m2.d.ts
│   ├── m3.d.ts
│   ├── textures.d.ts
│   ├── mpq.d.ts
│   └── utils.d.ts
```

The codegen's `dts` backend mirrors every `class_` / `enum_` /
`value_object` registration as a TypeScript declaration. Strict TS users
get full intellisense over every parser, writer, struct field, enum, and
constant.

Importing into TS:

```ts
import Whiteout from 'whiteout-wasm';
import type { mdx } from 'whiteout-wasm';

const w = await Whiteout();
const model: mdx.Model = w.mdx.parse(bytes);
```

## Memory & exception model

- **No exceptions.** WhiteoutLib's C++ side is built with `-fno-exceptions`;
  the WASM module is linked with `-fwasm-exceptions` only to interop
  cleanly with Embind's internals. Application code will never see a
  thrown exception from a parse / write call — bad input produces an
  empty result + entries on `parser.getIssues()`.
- **Manual lifetime management.** Every constructor returns an opaque
  handle to a heap-allocated C++ object. Always `try { … } finally {
  obj.delete(); }`. Forgetting to delete leaks WASM heap.
- **Vector mutation is read-modify-write.** Embind copies struct fields
  by value across the JS↔WASM boundary, so mutating a nested vector goes:
  `const v = obj.field; v.push_back(...); obj.field = v; v.delete();`.
  A `withField(obj, name, mutate)` helper in
  `tests/wasm/smoke.test.js` captures the idiom.

## Troubleshooting

| Symptom                                                           | Cause / fix                                                                                                            |
| ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `Cannot register type 'X' twice`                                  | Two binding TUs both register `X`. Usually means a hand-written entry in `bindings.cpp` duplicates the codegen output — drop the hand-written one. |
| `whiteout.mdx.Parser is not a constructor` (browser only)         | Dev server is serving a stale `whiteout.js` / `.wasm`. Clear `node_modules/.vite/`, hard-refresh (Ctrl+Shift+R), or restart the dev server. |
| `Failed to load whiteout.wasm` (Vite 403 on `/@fs/...`)           | The package lives outside Vite's project root. Add `server.fs.allow: ['../..']` (adjust to your tree).                  |
| `Aborted(both async and sync fetching of the wasm failed)`        | The `.wasm` sibling moved away from the `.js` loader — make sure both are co-located in the served path.                |
| `interfaces::WorkerPool is an abstract class` at compile time     | Codegen bug — a binding takes the abstract base by value. File a bug; the fix lives in `tools/codegen/emit_embind.py`.   |
